# Con architecture

How the code is organized: layers, modules, who calls whom, how a game launch and a stream work. What exactly the app can do is in [FEATURES.md](FEATURES.md); how to build it is in [BUILD.md](BUILD.md).

## Three layers

```
┌────────────────────────────────────────────────────────────────────┐
│ Layer 3. System shell, written for each system                     │
│   macOS:   Sole (SwiftUI), SoleMedia (decoder, display, sound)     │
│   Android: SoleAndroid + Platform/android + Android/CheckApp (Java)│
│   Linux, Windows: ConDesktop + Platform/desktop + Platform/login   │
│            (SDL 2, Cairo, FFmpeg; sign-in: WebKitGTK / WebView2)   │
├────────────────────────────────────────────────────────────────────┤
│ Layer 2. Shared Swift code, one for all systems                    │
│   SoleLogic  →  SoleCloud, SoleEngine  →  SoleCore                 │
├────────────────────────────────────────────────────────────────────┤
│ Layer 1. Rust: the engine (Engine/), C interface CConEngine,       │
│   and Con's platform code (Platform/), C interface CConPlatform    │
└────────────────────────────────────────────────────────────────────┘
```

The main rule: **everything that defines behavior lives in layer 2**. The shell only talks to the system (it draws, decodes, reads the gamepad, stores secrets) and does so through protocols declared by the shared code. The rule is checked by tests (`Tests/SoleCoreTests/PortabilityTests.swift`); more in [DEVELOPMENT.md](DEVELOPMENT.md).

## Modules

Dependencies (an arrow means "uses"):

```
Sole ──► SoleLogic ──► SoleCloud ──► SoleCore
  │          │
  │          └────────► SoleEngine ──► CConEngine (Engine/), CConPlatform (Platform/)
  └──► SoleMedia ──► SoleCore, CConPlatform

SoleAndroid ──► SoleLogic, SoleCloud, SoleEngine, SoleCore, CConAndroid
```

Shared modules may import only Foundation (and `FoundationNetworking` under `#if canImport`), each other, and the C interfaces of the two Rust libraries (`CConEngine`, `CConPlatform`).

Con's own code has two languages: Swift and Rust. Two C files remain, and they are not Con's code but one-line shim headers for SDL 2 and Cairo in `Sources/CSystem` (through them the Swift of the Linux and Windows shell sees the headers of those libraries); no new C may be added (test `testConsOwnCodeIsSwiftAndRust`).

### Platform: Con's platform code in Rust

What the shared Swift code takes from the system and cannot express in Swift itself (it has no sockets and no calls into a single system's C library). The crate `con-platform` (`Platform/`), a static library for each system (`Platform/build.sh`); its C interface is generated by cbindgen (`work/platform-rust/include/con_platform.h`, module `CConPlatform`). Every function exists on every system; where there is nothing to do, it does nothing.

| File | What it does |
|---|---|
| `net.rs` | Broadcast addresses of the computer's networks for console discovery (`con_broadcast_address_texts`): getifaddrs, on Windows GetAdaptersAddresses. |
| `wine.rs` | Only under Wine: small memory allocations above 2 GB, as Swift 6.4's `String` expects them (`con_wine_heap_active`); runs before `main` as a C runtime initializer (`.CRT$XCT`), see [WINDOWS.md](WINDOWS.md). |
| `objc.rs` | macOS: an Objective-C exception is caught instead of terminating the program (`con_objc_catch`, via objc2); in Swift it is `SoleCatchException` in `SoleMedia`. |
| `test_port.rs` | For tests: a UDP port that is open and not read (`con_test_udp_port_hold`). |

### Linux and Windows layer

`ConDesktop` (Swift: models, screens in Cairo, an SDL 2 window; one shell for both systems; the program `con`, on Windows `con-app.exe`), `Platform/desktop` (Rust, crate `con-desktop`, its own static library `con_desktop`, linked only into the app: libsecret or Credential Manager, FFmpeg for Store pictures and the stream, the SDL texture; C interface from cbindgen in `work/platform-rust/include/con_desktop.h`, module `CConDesktop`), `Platform/login` (Rust, program `con-login`: the sign-in window on gtk4 + webkit6, on Windows webview2-com with the WebView2 loader built in). ### Android layer

`SoleAndroid` (Swift: models on Android, the state snapshot for the screens, receiving their requests), `Platform/android` (Rust, crate `con-android`, its own static library `con_android`, linked only into `SoleAndroid`: JNI on the `jni` crate, MediaCodec and AAudio on `ndk-sys`; C interface from cbindgen in `con_android.h`, module `CConAndroid`), `Android/CheckApp` (Java: screens modeled on `Sole`; they make no decisions, they draw the snapshot and pass on presses). Details: [ANDROID.md](ANDROID.md).

## What the shell must provide to the shared code

Five protocols; a new system = their implementation plus screens.

| Protocol | Declared in | What it is | macOS | Android |
|---|---|---|---|---|
| `CredentialStore` | `SoleLogic/PSNAuthorization` | Secure sign-in storage: write, read, delete by name. | `KeychainCredentials`: Keychain through `SoleCredentialAgent` | `AndroidCredentials` on top of `Vault.java` (AES-GCM, key in Android Keystore) |
| `SonyLoginPage` | `SoleLogic/PSNAuthorization` | Sony's sign-in page in the system's web component; returns the code and the sign-in cookie. | WKWebView (`Sole/SonyWebsiteLogin.swift`) | `AndroidLoginPage` on top of WebView (`LoginActivity`) |
| `StreamPlayer` | `SoleLogic/AppModel` | What plays the stream. Usually it is the shared `StreamModel`. | `StreamModel` | `StreamModel` |
| `StreamDevice` | `SoleLogic/StreamModel` | The system's side of the stream: screen, sound, input, gamepad effects, "keep the screen on". | `MacStreamDevice` (`Sole/RemotePlay.swift`) | `AndroidStreamDevice` |
| `StreamMedia` | `SoleLogic/StreamModel` | Receiver of the picture and sound of one stream. Called from the engine's threads. | `FrameSink` (`Sole/RemotePlay.swift`) on top of `VideoPipeline` and `AudioPlayback` | `AndroidMedia` (MediaCodec + AAudio) |

One more, internal: `PictureGenerator` (`SoleCore/PictureQueue`), the generator of intermediate frames; on macOS it is `FrameInterpolator`.

## Signing in to the account

1. `AppModel.signIn()` asks `SonyLoginPage` to open Sony's page. The password is entered on Sony's page; the app does not see it.
2. The page arrives at the return address. `PSNCallback` checks `state` and extracts the code; the shell hands over the `npsso` sign-in cookie along with it (`SonySSO`).
3. `PSNAuthorization` exchanges the code for tokens and puts the refresh token and the cookie into `CredentialStore`.
4. On the next launch the sign-in is restored from storage without the sign-in page; parallel consumers share one refresh request.

Cloud permissions use the same cookie; there is no separate sign-in for the cloud.

## Launching a cloud game

The order is set by `CloudAuthorization.connect` (the player sees the texts in parentheses):

1. **License** ("Checking the game license…"). For PS5: a permission from the account server against the sign-in cookie → `CloudEntitlementService` matches the catalog game with the account's license. For PS4 / PS3: `PSPlusPCService` finds the product and makes sure of the streaming license.
2. **Session** ("Creating the game session…"). `CloudSessionService.begin`: from this moment Sony holds the account's session.
3. **Two permissions** ("Confirming your account with the cloud…", "…access to the game stream…"): the codes are short-lived and are requested right before use.
4. **Session authorization and locking** ("Preparing the game session…").
5. **Datacenters** ("Getting the list of servers…", "Measuring latency to the servers…"). The latency to each one is measured by the engine (`CloudNetworkProbe` → `con_cloud_probe_run`).
6. **Server selection and slot** ("Selecting server…", "Requesting a game server…"). Sony allocates a slot: address, port, keys. The slot's keys live only in memory.
7. `AppModel` hands the ready stream to `StreamPlayer`, that is, `StreamModel.connectCloud`.

A failure at any step turns into a `CloudFailure`: a text for the player and a flag saying whether it can be retried.

## Stream

`StreamModel.connectCloud` (and `connect` for a console):

1. Asks `StreamDevice` for a receiver: `openMedia(hevc:)` (PS5 is HEVC, the rest is H.264).
2. Creates the engine's `RemotePlaySession` with three closures: video, sound, events.
3. The engine connects and starts calling `media.video(...)` and `media.audio(...)` **from its own threads**.
4. On the connection event the phase becomes `streaming`; the model turns on input (`startInput`), asks to keep the screen on, and once a second takes metrics (`media.counters()` → `StreamMeter` → `StreamStats`).
5. Game events (vibration, triggers, light, a request to reset the sensors) are passed by the model to `StreamDevice`.

### Picture on macOS

```
engine ─► VideoStream (frame? key?) ─► PictureOrderBridge (numbers after losses)
       ─► VideoToolbox ─► PictureQueue ─► [FrameInterpolator] ─► PresentationClock
       ─► AVSampleBufferDisplayLayer
```

A frame is decoded before the reply to the engine: if the decoder rejected it, the engine learns about it at once, and the app asks for a keyframe. Losses, the numbering bridge and the display rhythm are analyzed in [VideoRecovery.md](../VideoRecovery.md).

After a loss the engine repairs the frames' references to reference pictures so that the decoder can go on, and marks frames with knowingly wrong content as "decode only" (`CON_VIDEO_FLAG_DECODE_ONLY`, in Swift `display: false` on `VideoHandler` and `StreamMedia.video`). Such frames are decoded on all systems (the following frames rely on them) but are not shown: the last correct picture stays on screen, for about 150 ms, until the server's recovery frame. They are not counted as a loss; on macOS `PictureQueue` does not receive them, and frame generation does not go through them. The engine's counters (`con_session_video_hidden`) are in `media-health.json` (`hiddenFrames`, `hiddenRuns`) and in the stats line on Android and Linux/Windows ("hidden N in M runs").

### Picture on Android

```
engine ─► VideoStream ─► LossGate ─► MediaCodec ─► surface of the stream screen
```

No frame generation; the display time comes from `PresentationClock`. What goes into the decoder is decided by `LossGate`: the engine hands over only frames the decoder can decode, so it holds nothing back; a keyframe is awaited only after a decoder failure and its restart. A "decode only" frame goes into MediaCodec as usual, and its output buffer is released without being shown (`releaseOutputBuffer(index, false)`). FFmpeg on Linux and Windows works the same way (`DesktopMedia`, `con_video_submit(…, show = 0)`).

### Sound and input

Sound arrives from the engine already decoded (16 bit): on macOS it goes to `AudioPlayback` (AVAudioEngine, a bounded queue, watches for changes of the output device), on Android to AAudio without waiting. Input: the shell reads the gamepad into the shared `PadReading` and the keyboard into the shared `Key`; from them the shared code (`KeyboardLayout`, `KeyboardPlay`, `MouseLook`) builds `ControllerState` and hands it to the engine.

## Remote Play with a console

`ConsoleDiscovery` finds consoles on the network → `RemotePlayRegistration` registers by an eight-digit code and returns keys → they are kept in secure storage → `StreamModel.connect` opens the same stream as for the cloud. An end-to-end session with a real console has not been tested yet.

## Threads of execution

- Models (`AppModel`, `StreamModel`, `LibraryScreen`) are on the main actor.
- The engine has its own threads. `StreamMedia.video` and `.audio` are called from them and must not wait for the main thread.
- Network is `async` on top of `URLSession`; stopping the engine goes into a separate task so as not to hold the main thread.
- On Android the Swift main queue is served by Android's main loop (`con_main_queue_attach`), so the library is loaded and started on the main thread.

## Engine

The engine is Con's own, in Rust (`Engine/`), written from the protocol description (`docs/protocol`); its C interface is generated by cbindgen from `Engine/src/ffi` (`work/engine-rust/include/con_engine.h`, module `CConEngine`). Console discovery, console registration, measurement to the cloud datacenters and the stream (console and cloud) run on it, on all four systems.

The engine library (`Engine/build.sh <target>`) is linked from `work/engine-rust/<target>/`, the platform code library (`Platform/build.sh <target>`) from `work/platform-rust/<target>/`, both together with the system libraries from `native-libs.txt` next to them (`Package.swift`: the engine with `SoleEngine`, the platform code with `SoleCore` and `SoleEngine`, so it is in every program of the package; on Windows `/include:con_wine_heap_start` keeps the heap initializer for Wine in it). The C interfaces are only module maps (`Sources/CConEngine`, `Sources/CConPlatform`, on Linux and Windows also `Sources/CConDesktop`: the `con_desktop` library from the same folder, with `native-libs-desktop.txt`, linked only into the app; on Android `Sources/CConAndroid`: the `con_android` library with `native-libs-android.txt`, only with `SoleAndroid`, because it calls Swift functions that the shared code's tests do not have; and `Sources/CConAndroidCheck`: `con_android_check`, only with the check program), with no C sources. Both libraries carry the Rust standard library as a separate archive member, and the linker takes it once, which works only if both were built by the same Rust (`Platform/build.sh` checks this):

| System | Target | Who names the folder |
|---|---|---|
| macOS | `aarch64-apple-darwin` | `Package.swift` itself |
| Android | `aarch64-linux-android`, `x86_64-linux-android` | `Scripts/build-shared-android.sh`, `test-shared-android.sh`, `check-android-run.sh` |
| Linux | `aarch64-unknown-linux-gnu`, `x86_64-unknown-linux-gnu` (depending on the build machine) | `Scripts/build-linux.sh`; in the virtual machine the engine library built on the Mac is copied into its `work/engine-rust/` (with `include/`), since `linux-vm.sh` does not transfer the `work/` folder; the platform code with the shell parts is built in the machine itself |
| Windows | `x86_64-pc-windows-msvc` (`con_engine.lib`, `con_platform.lib`) | `Scripts/build-windows.sh`, `test-shared-windows.sh` |

The build system is named by the variable `CON_SYSTEM` (`android`, `linux`, `windows`; without it, macOS), the library folders by `CON_ENGINE_LIB` and `CON_PLATFORM_LIB`; the scripts set them and stop if a library is missing.

What Con takes from the engine beyond discovery, registration and sessions (C interface version 2, `CON_ENGINE_ABI_VERSION`; the test `theLibraryWasBuiltForTheHeaderConUses` checks the header against the library):

- **Measurement to datacenters** (`CloudNetworkProbe.run` → `RustCloudProbe`, `con_cloud_probe_run` on Con's threads, one per datacenter). The result is the latency in ms, rounded; an MTU outside 576–1454 → 1454/1254. `diagnostics/cloud-probe.json` holds the stage on Con's 0–7 scale (`stage`), the engine's own stage (`engineStage`) and its code (`status`, `CON_PROBE_*`); the engine's error text is not written.
- **Latency to the slot**: the latency measured before the stream goes into `ConCloudConfig.rtt_us`; the engine shows it as the stream latency until its own first measurement.
- **Thread priority**: `con_set_thread_callback` is set once before the first launch (`RustEngine.prepare`); the media receive and output thread (`CON_THREAD_IO`) and the gamepad sending thread (`SENDER`) get `con_thread_set_interactive`: on macOS a quality-of-service class, on Windows `THREAD_PRIORITY_HIGHEST`, on Linux and Android nice −8 (Linux does not allow this to an ordinary user: `ulimit -e` = 0, except for groups like `gamemode`); session steps, the control channel and statistics get the user-initiated class (only on Apple systems).
- **Quit stage**: `ConQuitEvent.stage` → `RemotePlaySession.Event.quit(…, stage:)`; the line `quit … stage=<name>` in `stream-connection.txt` (`con_stage_name`). The engine version is there too, as the line `engine=rust <version>`.
- **Video recording** for analysis: the setting `sole.videoCapture` (Bool) or `CON_VIDEO_CAPTURE=1` (`0` turns it off even when the setting is on); off by default. The file `diagnostics/video-capture.bin` in the cache folder (`~/Library/Caches/Sole/…` on macOS; on other systems the Foundation cache folder) is replaced at every stream start (`ConSessionOptions.video_capture_path`), with `audio-capture.bin` next to it; they hold only the game's decrypted video and sound, without keys or account data. The format is in `docs/protocol/IMPLEMENTATION.md`, "Video capture". To turn on: `defaults write app.sole.desktop sole.videoCapture -bool true`; to turn off: `defaults delete app.sole.desktop sole.videoCapture`.

What Con does for the engine itself:

- **Broadcast addresses of networks** for console discovery (`con_broadcast_address_texts`, `Platform/src/net.rs`): the engine does not enumerate networks itself and takes them as a list (`extra_destinations`), and it sends to the limited broadcast address even without them.
- **Console targets**: `ConsoleTarget` stores the console generation as the same numbers Con has always stored it with (0, 800, 900, 1000, 1000000, 1000100), so consoles registered by earlier versions are read as they were; `RustMapping` translates them into the engine's `CON_TARGET_*`.
- **Gamepad state** (`ControllerState`, `Sources/SoleEngine/Controller.swift`): its own fields and button numbers; `RustMapping.controllerState` translates it into `ConControllerState`.

Opus: libopus is inside the engine library (renamed to `con_opus_*` and so on, `Engine/build.sh`); the app has no libopus of its own and no other third-party libraries.

## Tests as part of the architecture

Each shared module has a matching test suite (`Tests/<Module>Tests`), and they run both on macOS and on an Android device. The architecture rules (what may be imported where, where sockets are opened, how requests and sessions are made, which module holds which file) are written down as tests in `PortabilityTests`, not only in words.
