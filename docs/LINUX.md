# Linux version

Con for Linux is the same app as on Mac and Android: the shared code (`SoleCore`, `SoleCloud`, `SoleEngine`, `SoleLogic`) and the engine (`Engine/`, Rust; see [ARCHITECTURE.md](ARCHITECTURE.md), "Engine"), plus a shell shared with Windows (`Sources/ConDesktop`, see [WINDOWS.md](WINDOWS.md)). The target is an ordinary PC and the Steam Deck. It works from sign-in to stream on Ubuntu 24.04 (aarch64, virtual machine); there is no build for x86_64 (Steam Deck, ordinary PCs) and no installation package yet.

## What it is made of

```
con (Sources/ConDesktop, Swift)            window, screens, input: the program "con" (on Windows: con-app.exe)
   main.swift   window loop on the main thread; between iterations it drains the Swift main queue (RunLoop)
   Window.swift SDL 2: window, rendering, mouse, touch, keyboard, gamepad
   Screens.swift screens modeled on the Mac (Sources/Sole), drawn with Cairo/Pango from the shared models
   Draw.swift   drawing: colors, shapes, text (Pango), line icons, covers
   App.swift    AppModel, StreamModel, LibraryScreen, FocusModel; "state/stream/play" lines to the log
   Platform.swift keyring, sign-in window, video and audio input, stream device
Platform/desktop (Rust, module CConDesktop)  libsecret, FFmpeg (Store pictures and the stream), SDL texture
con-login (Platform/login, Rust)            Sony sign-in window: GTK 4 + WebKitGTK 6 (gtk4, webkit6), a separate program
Sources/CSystem/SDL2, Cairo                 SDL 2 and Cairo/Pango modules for Swift (pkg-config)
```

As on the other systems, the decisions are in the shared code: what to show, the launch order, what a press does, where the gamepad focus frame goes, what to hand the decoder after losses (`LossGate`). The shell draws and passes presses on.

| What | With what on Linux |
|---|---|
| Screens | SDL 2 (window, accelerated rendering, vsync) + Cairo/Pango (drawing the interface into a texture over the picture) |
| Stream picture | FFmpeg (software decoder, slices on all cores) → YUV texture in SDL; what to feed it is decided by `LossGate` (everything except frames after a decoder failure); frames the engine marks "decode only" are decoded and not drawn |
| Sound | SDL (PipeWire/PulseAudio), buffer of up to 1/5 second |
| Gamepad | SDL GameController: buttons, sticks, triggers; a DualSense gets the game's effects report whole (triggers, light, motors; the layout matches SDL's), another gamepad gets motors |
| Keyboard | SDL codes are the same USB codes as `Key` in the shared code; in a game, `KeyboardPlay` |
| Sign-in | `con-login`: Sony's page in WebKitGTK, ephemeral session; returns the redirect address and the cookie, as on Android |
| Sign-in storage | session keyring through libsecret (GNOME Keyring, KWallet) |
| Covers | FFmpeg parses JPEG/PNG/WebP, Cairo draws |
| Steam | in Steam's game mode (`SteamDeck`, `SteamGamepadUI`) the window goes full screen at once, and the Steam keyboard opens for search |

## Building

Needed (Ubuntu 24.04): the swift.org 6.4 compiler, Rust (`cargo`, if the engine is built here) and the packages

```
build-essential cmake pkg-config git libclang-dev
libsdl2-dev libavcodec-dev libavutil-dev libswscale-dev libcairo2-dev libpango1.0-dev
libgtk-4-dev libwebkitgtk-6.0-dev libsecret-1-dev
```

On the Linux machine itself, from the project folder:

```sh
Engine/build.sh $(uname -m)-unknown-linux-gnu     # engine → work/engine-rust/<arch>-unknown-linux-gnu (needs cargo)
Platform/build.sh $(uname -m)-unknown-linux-gnu   # platform code, shell library and con-login → work/platform-rust/<arch>-unknown-linux-gnu
./Scripts/build-linux.sh              # con (and con-login beside it) → work/linux/<arch>/con (release; debug as an argument)
CON_SYSTEM=linux swift test --scratch-path work/linux-build   # shared code tests
```

The engine for Linux does not have to be built on Linux: the library built on the Mac (`Engine/build.sh aarch64-unknown-linux-gnu`, swift.org clang with the Static Linux SDK headers) links and works on Ubuntu 24.04. It is copied into the virtual machine with `rsync -a -e "ssh -i $CON_LINUX_KEY" work/engine-rust/aarch64-unknown-linux-gnu $CON_LINUX_HOST:con-build/Con/work/engine-rust/` (`linux-vm.sh` does not transfer the `work/` folder). Without the library `build-linux.sh` stops; a different library folder is set with `CON_ENGINE_LIB`.

Con's platform code (`Platform/`, Rust, no C) for Linux is built **on the Linux machine itself**: together with it, `Platform/build.sh` builds parts of the shell, the library `libcon_desktop.a` (keyring through libsecret, FFmpeg, SDL texture; the FFmpeg interface is generated by bindgen from this system's FFmpeg headers and needs libclang) and the sign-in window `con-login` (the gtk4 and webkit6 crates on top of the system's GTK and WebKit). GTK and WebKit for Linux cannot be built on a Mac, so the Linux library built on the Mac does not contain these parts, and `build-linux.sh` stops with it. `cargo` downloads the Rust crates from crates.io on the first build (`~/.cargo/registry`), and installs cbindgen 0.29.4 itself. The engine and the platform code must be built with the same Rust version. A different library folder is set with `CON_PLATFORM_LIB`; Swift looks for the headers in `work/platform-rust/include`.

Linux does not give an ordinary user the priority of the engine's receive thread (nice −8) (`ulimit -e` = 0; Ubuntu's `gamemode` group has −10, which is enough): the thread then runs at normal priority.

From a Mac, through any Linux virtual machine reachable over SSH: `Scripts/linux-vm.sh '<command>'` transfers the project to `~/con-build/Con` on the machine (without `work/` and `Con.app`) and runs the command there, for example `Scripts/linux-vm.sh ./Scripts/build-linux.sh`. The machine and the key are set with `CON_LINUX_HOST` (`user@host`) and `CON_LINUX_KEY` (path to the ssh key), in the environment or in the file `work/linux-vm.env`.

`work/linux/<arch>/con` holds `con`, `con-login`, `Con.png`, `THIRD-PARTY-NOTICES.md` and `install-apparmor.sh`.

## Steam Deck: Flatpak, not the store

Con is distributed as a Flatpak package, not through the Steam store: it uses Sony's closed services on behalf of Sony's apps and the PlayStation trademarks, which store distribution would put at risk (a complaint from Sony to Valve, a risk for PSN accounts).

The package is described in `Linux/flatpak` and **has never been built yet**:

| File | What |
|---|---|
| `app.sole.Con.yml` | Package description: the GNOME 48 runtime (GTK 4, WebKitGTK 6, SDL 2, Cairo, Pango, libsecret), the Swift 6 and Rust extensions; it builds FFmpeg with decoders only (H.264, HEVC, JPEG, PNG, WebP), the engine (`Engine/build.sh`), the platform code with the shell library and `con-login` (`Platform/build.sh`; bindgen expects libclang from the SDK, whether it is there is not checked) and Con. **The engine build needs the network**: `cargo` downloads its crates (`Engine/Cargo.lock`) from crates.io, so the `con` module has the network open (`build-args: --share=network`); a local build allows this, Flathub does not (it would need a pre-recorded list of crates, `cargo-sources.json`). Program access: network, Wayland/X11, sound, all devices (gamepads, hidraw for DualSense), keyring. |
| `app.sole.Con.desktop`, `app.sole.Con.metainfo.xml`, `icon-256.png` | Shortcut, metadata, icon. |
| `build-flatpak.sh` | Build on Linux of the same architecture as the device (for Steam Deck, x86_64): installs the runtime from Flathub and writes one file, `work/flatpak/app.sole.Con-<arch>.flatpak`. |

On the Steam Deck (plan, not checked):

1. Desktop mode → copy the file over → `flatpak install --user app.sole.Con-x86_64.flatpak` (the GNOME runtime comes from Flathub).
2. Steam → "Add a Non-Steam Game" → Con.
3. Game mode → Con from the library: full-screen window, the Steam Deck's gamepad or a DualSense, the Steam keyboard for search.

Sign-in: inside Flatpak, WebKit builds its sandbox with Flatpak's own means; no AppArmor profile is needed.

## Ubuntu and the sign-in window

WebKit puts the page in a sandbox (bubblewrap). Since 23.10, Ubuntu allows this only to programs with an AppArmor profile, like its own browsers. Without a profile the sign-in window closes at once; Con then says what to run. Once, with administrator rights:

```sh
sudo ./install-apparmor.sh            # from the folder that holds con-login
```

The profile names only `con-login`, by its path (`/etc/apparmor.d/con-login`). On the Steam Deck (SteamOS) and most other systems this restriction does not exist.

## Checks

| Script | What it checks |
|---|---|
| `CON_SYSTEM=linux swift test` | Shared code tests on Linux. |
| `Scripts/check-linux-stream.sh "<part of the title>" [seconds]` | One live run of a cloud game on the account signed in on the machine: Con on an invisible screen (Xvfb :99) with the session keyring, `con --play`, a screenshot in the middle (`work/linux-stream.png`), the log (`work/linux-stream.log`). The last line is `result: <state>` (`streaming` when the stream ran; also `waiting`, `stopped`, `nogame`, `ended`); the exit code does not depend on it. Not earlier than a minute after the previous session. |

`con --play "<part of the title>"` starts the game as soon as the catalog has loaded. The log (stderr) gets lines `state: …`, `play: …`, `stream: phase …` and, every 5 seconds, `stream: figures …`, without names or secrets.

## Status

Tested on Ubuntu 24.04 (aarch64, virtual machine):

- The platform code, `libcon_desktop.a` and `con-login` build with `Platform/build.sh`, and their crate tests pass; `build-linux.sh` builds `con` with the engine library built on the Mac.
- The shared code tests pass under `CON_SYSTEM=linux swift test`.
- Catalog with covers (decoded by FFmpeg), game page with screenshots, settings, account section, stream panel (`con --snapshot` on Xvfb).
- Sign-in through `con-login` (with the AppArmor profile installed): the window opens, WebKit runs in the bubblewrap sandbox, and the sign-in is stored in the keyring. `con-login` prints three lines on stdout and exits with code 0 when sign-in ends, and exits with code 2 on wrong arguments.
- An earlier build streamed a PS5 cloud game (Cyberpunk 2077) at 1920×1080, H.265, 59 frames per second with sound; software decoding took 4–10 ms per frame in the virtual machine.

## What is missing

- A build for x86_64 (Steam Deck, ordinary PCs). The Flatpak package is described (`Linux/flatpak`) but has never been built: the description may have errors, and the Swift version in the Flathub extension may differ from 6.4.
- Checks on the Steam Deck: game mode, the Steam keyboard, the built-in controls.
- Gamepad checks: no gamepad has been connected to the virtual machine. DualSense effects and rumble are written from the SDL documentation.
- Hardware decoding (VA-API): the processor decodes the picture.
- DualSense feedback that arrives as sound (haptics), the gamepad's sensors and touchpad, the mouse as camera.
- Con's own on-screen gamepad and on-screen keyboard (on the Steam Deck, the Steam keyboard).
- Even frame presentation on a grid (`PresentationClock`): a frame is drawn at the nearest screen refresh.
- Remote Play with a console: written, not checked (no console).
- A live stream with the current engine (`Engine/`) under Linux.
