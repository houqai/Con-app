# What Con can do and what has been tested

A detailed description of the macOS app's features and of what confirms each of them. The short version is in the [README](../README.md); how it is built is in [ARCHITECTURE.md](ARCHITECTURE.md); the shared code on Android is in [ANDROID.md](ANDROID.md).

## Implemented

- Single sign-on through Sony's page in a separate WebKit window, with checks of the OAuth state and callback. QR/passkey are offered by Sony itself. Profile, game history, the public cloud catalog, search, favorites and a catalog cache.
- The refresh token, Sony SSO and console keys are stored in the Keychain through the unchanging SoleCredentialAgent. It checks the signature of the parent Con process before accepting requests; tokens pass only through private stdin/stdout channels and are not logged. The component is kept byte for byte between rebuilds, so that the partition cdhash in the file-based Keychain does not change. Dialogs are turned off in Con and in the storage component. Operations run on a serial background queue. Old records are migrated only when they can be accessed without a dialog. Concurrent consumers share one refresh request. Cloud grants use the same Sony session; a separate sign-in in settings is not needed.
- The PSN profile avatar in the sidebar and in settings.
- Recent-game cards and catalog cards have the same width. Cards carry no platform labels. Settings and the game card close on a click outside and on Escape.
- The engine is Con's own, in Rust (`Engine/`), connected through SoleEngine: discovery of local PS4/PS5 consoles, registration by code, launching Remote Play and cloud streams, measuring latency to datacenters, gamepad input. Registration keys are stored in the Keychain; consoles registered with earlier versions are read as they were. Tested live: the PS5 cloud and PS4 on macOS (with DualSense effects) and the PS5 cloud on Android. The "My consoles" section (Remote Play) is hidden in all versions until it is tested with a console; `Destination.consolesShown` in `Sources/SoleLogic/Game.swift` turns it on.
- H.264 video goes to AVSampleBufferDisplayLayer with its own memory buffer. Opus audio is decoded and the PCM is played through AVAudioEngine with a bounded queue. On cancel, old video/audio callbacks are blocked; a new session gets its own decoder. Stopping the engine does not block the main thread.
- Our own Swift module SoleCloud: configuration, cloud authorization, session lock, the datacenter request, ICMP latency estimate, server choice, the slot allocation request and waiting in the queue. Slot keys are kept only in memory.
- The account's earlier cloud session: Sony holds the session for about a minute after a stream ends, and a launch right after leaving a game gets "the account already has a cloud session in progress" (the `lock?forceLogout=false` step answers `lockAcquired` ≠ true). Con decides by itself (`AppModel.startCloud`): if Con's own stream ended less than 3 minutes ago (the end time is in the settings, `sole.cloudStreamEndedAt`), that session is its own, and the launch of the same game is repeated at once with `lock?forceLogout=true` (the step "Ending the other session…"; Sony does not end it at once, so a forced lock without `lockAcquired: true` is repeated every 5 s for up to 40 s; Sony usually releases the session within about 15 s; the step "Ending the other session… (N s)"). Otherwise the session may be on another of the player's devices, and Con does not end it: the launch is repeated the normal way up to 6 times every 15 s ("The previous session has not closed yet. Trying again in 15 s (attempt N of 6)"), and the same happens after code 002.2008 ("Sony is still preparing the server"); the wait is cancelled like the whole launch, and if the session does not end in time, the message is "The account still has a cloud session… Start again when it is over." Every answer of the `lock` step is written to `diagnostics/cloud-lock.json` (overwritten): HTTP status, whether it was forced, the attempt number, the time, header names and the structure of the response: field names and types (and one level deeper), values only for booleans, small integers and short state words (not identifiers, keys, addresses).
- Checking an existing game license through Sony Commerce: the catalog productId is matched to the entitlementId before launch. There is no extra sign-in window. The allocate request carries the port chosen by Sony, the actual preparation time and the set bitrate. The queue uses a monotonic clock. Diagnostics keep only the error structure, numeric codes and fixed categories, without tokens and without the response text.
- Frame generation: SoleMedia VideoPipeline decodes the stream through VideoToolbox and, when generation is on, inserts a frame made by FrameInterpolator (macOS 26+) between neighboring frames. The computation runs ahead, and frames are shown on a schedule; every received frame comes out later by the computation time plus half an interval. It is turned on in the stream settings and with a button during a stream. A game that draws 30 frames in a 60 fps stream is recognized by repeated pictures (PictureCadence): a made frame is placed between two different pictures, and a repeat is not interpolated. A made frame is computed from copies of the pictures no larger than the size chosen in the stream settings ("Generation resolution", 720p by default) and no larger than the system generator on the Mac accepts, and it has that size. Frames are made only when the screen can show them (the game draws at no more than half the screen's refresh rate: 30 fps at 60 Hz, 60 fps at 120 Hz); otherwise no frames are made and there is no added delay. After three generator errors in a row, frames are no longer made, also with no added delay. While frames are being made, the stats line shows after the frame count how many of them are made ones ("60 +30").
- Frame loss: after a loss Sony's server sends a frame built on an older long-term reference picture. Frames in the stream are numbered with four bits, and when eight or more frames are skipped (at a ping of about 100 ms, every time) the decoder gets the number wrong by a whole cycle, looks for the reference picture in the wrong place and rejects that frame and all the following ones (VideoToolbox, code −12909). PictureOrderBridge (shared code, SoleCore) sees the skip from the engine's frame counter and, before such a frame, decodes copies of it with the intermediate numbers: a copy changes a few header bits, and the picture is the same. The image continues 150–200 ms after a loss, without waiting for a keyframe. Consecutive frames are not changed.
- Decoder failure: after one undecoded frame VideoToolbox rejects all the following ones until a keyframe. So a frame is decoded before answering the engine, the engine learns of the failure, and Con asks the server for a keyframe. Sony sends it about 1.2 seconds later; for that time the picture freezes, then recovers. A frame built on a lost picture is handled the same way: it is not decoded at all, so that a distorted image is not shown.
- Presentation rhythm: PresentationClock (shared code, SoleCore) gives pictures a display time on an even grid that runs 21 ms ahead of their arrival and follows the stream (the step is the measured stream interval, 59.94 fps in the cloud). The AVSampleBufferDisplayLayer layer keeps a picture's time only if it got the picture about 20 ms ahead; a picture stamped "now" is shown at a random screen refresh, which on a 60 Hz screen gives several doubled and skipped frames per second. Measured on screen: 7–20 times fewer rhythm glitches, and the delay from frame arrival to the screen is 8 ms longer. It is turned off in the stream settings ("Smooth presentation") and also applies to a stream in progress. Details are in VideoRecovery.md.
- Interface language: English by default; in settings ("General" → "App language") you can choose Russian, German, Spanish, French, Italian, Polish, Portuguese (Brazil), Japanese, Korean and Chinese (Simplified). The translations into the nine other languages are machine-made and have not been proofread by native speakers. The same eleven languages are offered as the "Game language" in the stream settings.
- The gamepad focus frame looks like the one on the selected game in the catalog: white, with an even gap, following the shape of the object (buttons, filters, switches, lists, settings tabs).
- The library opens straight to the game list. Clicking a game (or Enter, ✕ on the gamepad) opens its page over the whole window: cover, title and the buttons "Play", "Add to favorites", "PS Store"; back is the "Catalog" button, Escape or ○. A game launches only from its own page.
- Stream overlay: a control panel in the top left corner: "Disconnect" and round buttons for stats, frame generation and full screen. The panel appears when the pointer moves and goes away after three seconds of rest, together with the pointer; returning to the app also shows it. Stats are a thin line (30 points high, dark glass with a corner radius of 9, 12-point font with fixed-width digits) to the right of the buttons, aligned to their middle; when the buttons go away, it moves into the corner. It has four items, each with a dim icon and a value, without words: frames per second (film strip; for a 30 fps game its 30, with generation including the made frames and "+N" after the number), ping (Wi-Fi; during a stream the median of the last five measurements, before them the measurement taken before launch), bitrate (down arrow, "17.9 Mbps"), video (screen, "1080p"). In a narrow window the bitrate goes first, then the video. Losses are not shown separately: the ping icon is green while all is well, orange while frames are being lost, red on a decoder failure or a loss of half a second of frames or more; three seconds after the losses it is green again. The server and resolution are in the stream menu (the PS button or "Menu"; on the Mac and Android the latency too); codec and decode time are not in the line (the Linux, Windows and Android log has them in the `stream: figures` line). The line is the same for macOS, Linux, Windows and Android (`StreamPanel` in SoleLogic). While a stream is running, the screen does not turn off or dim. The DualSense light bar is lit: the color comes from the game, and when the server sends black (PS Cloud does this), Con's own blue.
- Keyboard control during a stream, together with a gamepad or without one. The default layout: movement is W A S D (left Option to walk), camera is the arrows, ✕ is space, ○ is left Shift, □ is E, △ is Q, R1 and R2 are F and R, L1 and L2 are V and C, L3 and R3 are left Control and right Shift, the d-pad is I J K L, Options is Esc, Create is Y, touchpad is T, PS is P. Keys are set by their position on the keyboard and do not depend on the input language. Each one can be changed in the "Controls" settings; a key that is already taken swaps places with the old one. Key presses during a stream do not reach the rest of the app; Command shortcuts work as usual.
- Mouse camera: a click on the picture during a stream captures the mouse: the pointer is hidden, mouse movement tilts the right stick in proportion to speed (MouseLook in SoleEngine), and the left and right buttons press R2 and L2 or R1 and L1. The Command key returns the pointer; so do leaving the app and the end of the stream. Turning it on, sensitivity and button assignment are in the "Controls" settings.
- Game sound is bound to the output device that was the system default at start and follows changes to it: when another device becomes the system default (headphones taken off, another output chosen), output restarts on it with the next buffer.
- The "PSN Account" settings tab: under sign-in are trophies and recent games. Trophies: level, progress to the next level, counts by grade (platinum, gold, silver, bronze) and four lists of the most recently updated trophies (icon, title, platform, how many earned, percentage). They are fetched from Sony (`m.np.playstation.com/api/trophy/v1/users/me/trophySummary` and `trophyTitles`) with the same sign-in token as the game history, at sign-in and on "Refresh library"; they are kept between launches (`sole.trophies`). If Sony refuses this token (HTTP 401/403), the page shows a quiet line "Sony does not show trophies for this sign-in."; `diagnostics/trophies.json` holds only the HTTP statuses of the two requests and whether they were read (no response bodies). Recent games are up to the last ten from the same game history (`gamelist/v2`), with cover, title and when they were played ("Today", "Yesterday", "N days ago" or a date); a press (mouse, touch, gamepad ✕) opens the game page. There are lines for loading, an empty list and an error. macOS, Linux, Windows, Android.
- Trophies during a cloud game: Sony's stream carries nothing about them (the Portal learns them from PSN), so at the start of a game Con remembers the account's trophy lists (`trophyTitles`) and reads them again every 30 s; for a list where the number of trophies grew, it asks which were earned after the start (`users/me/npCommunicationIds/{id}/trophyGroups/all/trophies`), and their names, grade and image in the app language (`npCommunicationIds/{id}/trophyGroups/all/trophies`). A notification at the top right for 6 s, one at a time: image, "Trophy earned · Gold", title. `diagnostics/trophy-watch.json` holds only the HTTP statuses and how many were shown. The "Trophy notifications" switch in "Stream" (on by default, `sole.trophyNotices`): when it is off, nothing is asked of Sony. macOS, Linux, Windows; on Android it is more compact: at the top in the center, a 32 dp image, grade and title on two lines (under the buttons, if they sit in the middle next to the on-screen gamepad).
- The "Purchased" filter in the library: the cloud catalog games for which the account has a valid full-game license, as in Sony's app: purchases and games obtained through a subscription together. The list is read at sign-in with the same license request as at game launch, and is kept between launches; the selected library section is remembered. A license for another edition or region of the same game is matched to the catalog by title; launching a game checks the license again.
- The app bundle contains no third-party dynamic libraries: the engine with its libopus is linked statically. The executables have no dependency on /opt/homebrew paths. The build is for Apple Silicon; the app declares macOS 26.0 as sufficient, and `Scripts/verify-release.sh` checks everything its files ask of the system against the macOS 26 SDK (launch tested on macOS 26.6).

## Testing and current limits

The test suite covers: Swift modules, HTTP response handling, packet formats, video buffer ownership, the decode and generation pipeline on a real codec, game frame rate detection, frame numbering recovery after losses, audio conversion, translation of engine events, sessions and the engine's measurement on loopback, starting/stopping discovery. The release build and signing have been checked.

Confirmed on a real account: profile restore, both cloud OAuth grants (the clients for virtType=cronos, OAuth v3), authorization and lock of the chosen game session, the datacenter list and the server selection request, and the UDP network test (Senkusha) on Sony's servers (5 datacenters, about 3.5 seconds). Allocation needs a measured latency for the chosen datacenter: without one, select answers 200 and allocate rejects the session key (HTTP 403 / 002.2005). With real measurements Sony answers already at select with HTTP 400 / 002.0019 if no datacenter has a latency under 80 ms. By default Con keeps this limit: when the chosen datacenter is further than 80 ms, the game does not start and Con says how far the server is and that the Distant servers setting allows it. With Distant servers on (Settings → Stream, off by default), Sony is sent 75 ms instead of the measured latency above 80 ms (`CloudPingPolicy`); the interface and diagnostics keep the measured value. With this substitution select and allocate go through, tested from a network about 105 ms away from the nearest datacenter (Tokyo). This departs from the service's rules: noticeable input latency and a risk to the account are possible. If Sony is still freeing the slot of the previous session (HTTP 500 / 002.2008), the request is repeated for up to a minute and a half.

Datacenter names are shown as cities (CloudDatacenterName). Sony sends the datacenter list only while preparing a stream, so the last list and the chosen server are kept between launches.

On a test record the following were confirmed: saving through the storage component, reading after the Con executable changed, and refusal to a foreign parent process. A real account's sign-in is also restored after the Con executable changes, without a password window. Records from older versions (app.sole.psn.v2/v3) were bound to the cdhash of the earlier app, so if such a sign-in cannot be read, the user signs in to Sony once more.

### Tested end to end

- PS5 cloud game on Sony's server in Tokyo (Demon's Souls): HEVC video at 60 frames per second in the 1280×720 profile, sound with a non-zero level, gamepad input (button presses skipped the intro and went through the title screen); ending the stream and quitting the app send the server a disconnect.
- Frame generation on the same stream: +56 frames per second with a computation of about 10 ms and an added delay of 18 ms.
- Recovery after losses: on recorded frames of four real losses in this stream (without PictureOrderBridge VideoToolbox rejected 1, 10, 66 and 61 frames in a row, with it none, and the picture matches the next keyframe) and on a live stream: one real loss (11 frames) and three artificial ones passed without decoder errors, and the image resumed after about 150 ms.

### Limits

- In the end-to-end test the button presses were sent by a program, not a physical gamepad; sound volume and sync were not checked by ear.
- The smoothness gain of frame generation was measured on a 60 Hz screen, where it is not visible.
- Loss recovery was tested only in the 1280×720 profile; if in another profile Sony splits a frame into several slices or describes the reference pictures differently, the bridge does not step in and the keyframe request does the work.
- Remote Play with a console uses the same pipeline, but an end-to-end session with a real console has not been tested yet.

## PS4 and PS3 clouds

The PS4 cloud ("PS Now"): a separate Swift backend (`PSPlusPC`) adds PS4 cloud games to the catalog after sign-in. Bloodborne was launched at 1080p, H.264, Takion 9 transport with the UDP 1 wrapper. PS4 sound (packed main and backup Opus parts) is parsed separately from PS5 cloud sound. A missing streaming license is activated only if Sony confirms exactly one matching product with an explicit zero price; paid and unclear prices are rejected. Each catalog game was not tested individually.

The catalogs are separate: PS5 and PS Now (PS4) have their own source tabs and shared filters "All", "Purchased", "Recent", "Favorites". PS Now cards load up to six screenshots on request from Sony's regional product page. The PS5 cloud protocol is chosen by `connect_info.ps5`, because the target of the cloud negotiation remains PS4 (the bug fix is in [SoleCloud.md](../SoleCloud.md)). Repeated live tests: both streams at about 60 received frames per second, without decoder errors; occasional network losses remain.

The PS3 cloud: a separate catalog source matches the old product identifiers (NP/BL/BC) to streaming licenses. Sessions use the "konan" allocation, the PS3 client permission scope without a device identifier, Takion 9 transport and a 720p limit. Tested live: Alone in the Dark: Inferno reached the game menu at 1280×720, H.264, the menu responded, the sound was not silent, zero sound and decoder errors. The stream: 60 frames per second received, 30 shown; there were brief frame losses during the test, so this is not a claim of loss-free operation and not a test of every PS3 game.

## Android

The same shared code runs on Android in the Con app for Android, with screens modeled on the Mac: sign-in, a catalog with covers, the game page, settings, consoles, an on-screen gamepad, a stream that goes on while the app is minimized, a cloud stream (Cyberpunk 2077, PS5 cloud, 1920×1080 H.265 with sound). What exists and what is missing is in [ANDROID.md](ANDROID.md).
